# Design

## Context

用户对着截图提了两件事：「素材信息往下来一点，留出更多空间给素材本身」和「瀑布流排列模式下，这种显示比较长的视频排版很怪」。第二件是主诉，而它不是一个视觉问题，是一个**同源问题**：同一个素材比例被两个地方各算了一遍，算法还不一样。

- `Card.tsx` 把原始 `a.width / a.height` 直接写成 CSS 变量 `--ar`，`.thumb{aspect-ratio:var(--ar,4/3)}` 按它渲染。
- `Grid.tsx` 的 `estHeight` 把同一比例 clamp 到 `[0.5, 3]` 再乘列宽，作为虚拟化的列内定位高度。

两者对常规素材一致，对极端素材分岔。1200x172（6.98:1）在 232px 列宽下：CSS 渲染 33px，占位预留 464px。

## Goals / Non-Goals

- 目标：极端比例的素材在瀑布流里不再塌成横线或撑出空档；卡片信息区的可读性与视觉重心回到素材本身；收藏按钮的两种状态在夜间主题下都能看清。
- 非目标：不改网格视图（强制 4:3）与列表视图（固定 96x58）的缩略图规则；不改缩略图生成、缓存与协议（`thumbnails` 能力）；不改 `object-fit`（CSS 素材的 900x675 渲染尺寸本身就是 4:3，`cover` 对它零裁切）；不改选中环的 `box-shadow` 外溢（属既有取舍）。

## Decisions

### 1. 比例收敛放在一个纯函数里，而不是在两处各写一遍

```ts
// src/renderer/src/data/thumb-ratio.ts
export const MIN_THUMB_AR = 1 / 2
export const MAX_THUMB_AR = 21 / 9
export const FALLBACK_THUMB_AR = 4 / 3

export function thumbRatio(width?: number, height?: number): number | undefined {
  if (!width || !height) return undefined
  return Math.min(MAX_THUMB_AR, Math.max(MIN_THUMB_AR, width / height))
}
```

`Card.tsx` 与 `Grid.tsx` 都从它取值，`undefined` 表示「交给 CSS 的 4/3 兜底」。这样两个文件之间只剩一处耦合，而不是两处独立实现。「必须同源」这条约束写进了注释和 spec，因为它是这两个文件唯一需要保持同步的地方。

### 2. 上下界取 `1/2` 与 `21/9`，不是随便挑的

- **下界 `1/2`**：9:16 竖屏视频是 `0.5625`，必须完整保留（这是手机拍摄素材的常见形态）；再瘦的就只剩长截图了，截掉一部分比把整列拉长得好。
- **上界 `21/9`（约 `2.333`）**：标准宽银幕是 21:9，保住它就不会误伤正常电影素材；比它更宽的（字幕条、全景长条）按 21:9 显示，由 `object-fit:cover` 居中裁切。

旧实现的 `[0.5, 3]` 上界 3 反而更松（16:9 的 1.78 与 21:9 的 2.33 都在界内），真正的问题是**这个 clamp 只作用在估高一侧，CSS 一侧没有收敛**所以不是「值选错了」，是「只有一个地方做了」。

### 3. 信息区几何：缩略图 80%、信息区 20%

诉求是「素材信息往下移，把空间让给素材本身」，落地为面积配比而不是内边距微调：
`figcaption{padding:12px 10px 11px}`  `7px 10px`，`.name` 与 `.meta-row` 的 `line-height` 显式写成 `15px` / `13px`，
`Grid.tsx` 的 `CAPTION_H` 由 `61` 改 `44`（7+7+15+13+2）。

实测（232px 列宽）：缩略图 173px、信息区 44px、卡片 219px，**缩略图占 79.0%**。
信息区高度是常量，不随列宽变化，所以列宽越大缩略图占比越高：170px 列宽 74.4%、232px 79.8%、320px 84.5%。
极端比例素材因为缩略图本身矮，占比自然低于 80%（1200x172 视频卡 68.3%），这是收敛后的正常结果若强行凑成 80%，
信息区就得随比例浮动，那才是真正的不一致。

中途被推翻的两个推断记在这里以免重犯：一是评审阶段认为「上下各 12px 后信息区仍是 61px」，实测是 62px；
二是最初把诉求理解成「给信息区加内边距」，实际要的是缩略图占比 80%。**结论是 `CAPTION_H` 与
`figcaption` 内边距、`.name`/`.meta-row` 行高存在硬耦合**，已在两处注释里互相指认。
### 4. 收藏按钮用「双通道」表示状态，不只用颜色

`.qa button` 底色 `.55`  `.72` 并把描边从无到 `1px solid rgba(255,255,255,.18)`；`.qa .fav.on` 底色加深到 `.82` 并吸附 `.ic{fill:currentColor;stroke:currentColor}`。

只用颜色区分状态对色觉障碍用户等于没有状态；实心心 + 更深底的组合让「已收藏」在灰度和形状两个通道上都成立。白图标对比度实测从 4.35:1 提到 8.09:1（正好越过 AA），粉心从 1.75:1 提到 3.26:1（大图形 AA 门槛 3:1）。实心图标靠 CSS 完成，不必改 `Icons.tsx` 的 symbol。

### 5. 渐变起点从 62% 推到 78%

`.thumb::after` 的压暗渐变原本从 62% 起，纯白缩略图有 **38% 的面积**被压到 `#B8B8B8` 及以下。推到 78% 并加强到 `.34` 后，压暗面积降到 22%，同时徽章底部的可读性没有下降（`.type-chip` 自带 `rgba(10,12,16,.62)` 底，不依赖这层渐变）。

## Risks / Trade-offs

- **`CAPTION_H` 与 `figcaption` 内边距的耦合没有被类型系统保护。** 若将来有人只改 CSS 不改常量，瀑布流虚拟化会重新错位。缓解：两处注释互相指认 + spec 里写明；彻底的解法是把信息区高度做成 CSS 变量由 JS 读取，属后续工作。
- **`MIN_THUMB_AR = 1/2` 会让 1:2 以下的超长截图被裁掉上下两端**（截图类素材的顶部标题或底部状态栏可能落在裁切区）。这是「保住瀑布流布局」与「完整展示」之间的取舍，选了前者。
- **`MAX_THUMB_AR = 21/9` 会让超过 21:9 的素材损失横向内容**（字幕条、全景图）。同样是有意为之：完整比例在灯箱里看。
- 渐变起点右移 16% 后，缩略图底部 22% 的压暗区更窄，`.type-chip` 与 `.dur` 之外若将来新增底部浮层元素，可借用的对比度缓冲变小。

## Open Questions

- 极端比例素材是否应在卡片上加一个「已裁切」的可视提示？当前没有任何提示，用户可能不知道看到的是裁切版。
- 信息区高度是否要改由 `ResizeObserver` 实测而不是常量？当前靠注释维持同步。
- 触屏 / 无悬停设备（`@media (hover:none)`）下 `.qa` 常显按钮的新底色**未在真机验证**本条改动的对比度实测都在有悬停的桌面窗口上完成。
- 浅色主题的信息区与浮层按钮**未重新采样**：本轮只解决夜间主题的对比度问题，浅色主题下 `.meta-row` 的 `--t2` 原为 8.51:1、`--t3` 为 4.51:1，改后只升不降，但未经像素复核。
