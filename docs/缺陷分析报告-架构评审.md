# MediaHub 素材管理器 — 架构缺陷分析报告

> 评审视角：软件架构师 · 范围：模块边界 / IPC / 状态管理 / SQLite 数据层 / 错误处理 / 可测试性 / 性能 / 安全
> 依据：docs/ARCHITECTURE.md、src/AGENTS.md、openspec/ 全部精读与抽样源码（main · preload · renderer · services · tests）

---

## 0. 总体结论

整体是一个**边界意识良好、单进程单文件快速演化**的本地优先应用：services 层职责划分、`media://` 路径校验、原子写、原子迁移等基础功是扎实的。但存在四类系统性风险：

1. **安全面扩张未被收口**：`media://` 特权（bypassCSP）+ 无 sender 校验 + 薄 preload 转发，构成「渲染层一旦被注入即全库可读」的组合拳。
2. **IPC 层是上帝模块**：ipc.ts 763 行承载全部 handler + 迁移副作用 + watcher 生命周期，零测试覆盖。
3. **全量同步架构**：主进程任何变更 → 渲染层全量 reload → 全量重过滤重渲染，事件高频时性能崩塌。
4. **错误处理无协议**：`{error}` 返回 / throw / 静默吞错 / alert() 四种风格并存。

统计：**设计缺陷 12 条 · 实现缺陷 21 条**。S0（严重）4 条，S1（高）11 条，S2（中）12 条，S3（低）8 条。

---

## S0 — 严重（安全 / 数据完整性 / 崩溃级）

### S0-1 【安全｜设计】media:// 特权配置过宽 + 协议 handler 无来源校验
- **位置**：`src/main/index.ts:98-100`；`src/main/media.ts`（全文，无任何 origin/frame 检查）
- **问题**：`registerSchemesAsPrivileged` 赋予 media 协议 `{stream:true, supportFetchAPI:true, bypassCSP:true}`，而协议 handler 只校验路径在库根内（`realPathWithinRoot`），不校验发起方。三个特权叠加意味着：渲染层任何帧（包括未来被塞进来的 iframe、第三方 HTML 预览内容）都能 `fetch('media://<libId>/<任意路径>')` 读到全库素材；`bypassCSP` 还使页面级 CSP 无法拦截。
- **影响**：CSS 预览等「渲染半可信内容」的场景是现实攻击面——被注入脚本后可静默拉取全库文件并外发（该应用虽本地优先，但任何未来联网功能都会激活此路径）。
- **修复方向**：① 移除 `bypassCSP`（无明确必要）；② handler 内校验 `request.referrer`/`frame` 仅允许主 frame 与应用自身 origin；③ 若需保留 fetch 能力，用 CSP `connect-src media:` 显式白名单替代 bypassCSP。

### S0-2 【安全｜实现】shell:show-in-folder 无路径校验，渲染层可探测任意磁盘路径
- **位置**：`src/main/index.ts:205-207`；`src/preload/index.ts:13-15`
- **问题**：主进程 `typeof p === 'string' && p` 即调 `shell.showItemInFolder(p)`，preload 原样转发任意路径。与 media:// 的「先 realPathWithinRoot 再动」约定完全不符。
- **影响**：被注入的渲染层可对任意路径调用——探测文件是否存在（返回行为差异）、在资源管理器中打开敏感目录。preload 的「薄转发 + 主进程兜底校验」模型在此处断链。
- **修复方向**：主进程校验路径必须经 `realPathWithinRoot` 落在某库根内；库外直接拒绝并返回错误。

### S0-3 【崩溃/数据完整性｜设计】libHandle LRU 驱逐会 close 仍被持有的活跃句柄
- **位置**：`src/main/services/libraryDb.ts:210-215`（getLibHandle，LRU 上限 8）
- **问题**：句柄缓存超过 8 个库时驱逐最旧条目并 `close()`，但进行中的调用方（如长事务 `upsertScanned`、scan 流程中缓存的 db 引用）仍持有旧句柄继续读写，将抛 `This database connection is closed`。
- **影响**：多库用户（>8 个库）在扫描/监听并发期间出现随机性、不可复现的崩溃式报错；写入中断可能留下半截事务（better-sqlite3 事务本身原子，但应用层重试逻辑缺失）。
- **修复方向**：① 驱逐前检查引用计数（in-flight 计数），为 0 才 close；② 或驱逐改为「标记待关 + 下次 get 时真正关闭」；③ 或把上限提到 64——句柄成本远低于崩溃风险。

### S0-4 【数据完整性｜设计】全局库迁移非事务、非幂等，失败即半截 schema
- **位置**：`src/main/services/db.ts`（V1–V5 顺序迁移，V2–V5 的 `ALTER TABLE` 无幂等保护，无事务包裹）
- **问题**：迁移依赖 `user_version` 正确推进；若迁移中途崩溃，`CREATE TABLE IF NOT EXISTS` 可重入但 `ALTER TABLE` 会重复执行而报错，库永久打不开。同文件 `openMemoryDb` 直接跑全部 schema，掩盖了该问题（测试环境与真实路径不同）。
- **影响**：升级中断（进程被杀/断电）后应用无法启动，且无自修复路径——这是本地优先应用最致命的故障模式。
- **修复方向**：每个版本步进包 `BEGIN/COMMIT`（成功后才 `PRAGMA user_version`）；ALTER 改为 `libraryDb.ts` 已有的 `table_info` 幂等检查模式（**同一仓库内已有正确实现，统一即可**）；补一条「模拟中断重放迁移」的测试。

## S1 — 高（架构 / IPC / 数据层 / 性能）

### S1-1 【设计】ipc.ts 是 763 行上帝模块：handler + 迁移 + watcher 生命周期 + 进度推送
- **位置**：`src/main/ipc.ts`（全文单函数 `registerIpc` 内联全部 handler）
- **问题**：库作用域解析、迁移副作用、缩略图预热队列、根 watcher 回调、全部业务 handler 揉在一个注册函数里；模块级可变状态（`watchers` Map、`migrationFailures` 无界数组）散落其中。
- **影响**：不可测试（见 S1-11）、不可审阅、任何新 handler 都在这个文件上继续堆积；模块级状态无生命周期管理。
- **修复方向**：按域拆 `ipc/assets.ts`、`ipc/libraries.ts`、`ipc/watch.ts` 等；`registerIpc` 只做注册与依赖注入（传入 services）；watcher 生命周期收敛为显式的 WatchManager。

### S1-2 【设计】scopeFor 混入一次性迁移副作用，且每次调用都执行
- **位置**：`src/main/ipc.ts:47-58`
- **问题**：作用域解析函数内嵌「stray library_id 重打」逻辑——migrated 时每次都跑 `SELECT 1`，命中则全表 `UPDATE`。幂等但每次 handler 调用都付这笔税。
- **影响**：作用域解析本应是纯函数；副作用使它不可测试、不可缓存，且语义上「解析作用域」与「修数据」是两件事。
- **修复方向**：迁移在启动时执行一次（library:migrate 已有该时机）；scopeFor 退化为纯查表。

### S1-3 【设计】事件推送只发 getAllWindows()[0]，多窗口/无窗口丢失
- **位置**：`src/main/ipc.ts:31-33`（send）
- **问题**：`BrowserWindow.getAllWindows()[0]?.webContents.send(...)`。
- **影响**：当前单窗口尚可，但 close→hide（托盘化）后 `getAllWindows()` 仍非空时序不确定；未来多窗口（设置窗、预览窗）出现即静默丢事件——渲染层状态与主进程脱节且无告警。
- **修复方向**：遍历 `getAllWindows()` 广播；事件常量与发送函数收敛到 `events.ts`（该文件目前只有 179B 的 4 个通道常量，正是它该做的事）。

### S1-4 【实现】assets:update 值不校验，SQLite 动态类型吞下脏数据
- **位置**：`src/main/ipc.ts:444-460`；`src/main/services/store.ts:108-114`
- **问题**：列名有 `EDITABLE` Set 白名单（安全），但值无类型校验——`rating` 可传字符串、`deleted_at` 可传任意值，SQLite 动态类型照单全收。
- **影响**：脏数据入库后 `queryAssets` 的比较逻辑（数值排序、时间解析）行为未定义；污染会随 upsert 持续传播。
- **修复方向**：每列声明类型校验器（zod 或手写窄化），在 handler 边界拒绝；`store.updateAsset` 二次校验列值类型。

### S1-5 【实现】assets:move 循环逐条 SELECT/UPDATE，无事务，中途失败留部分状态
- **位置**：`src/main/ipc.ts:548-581`
- **问题**：循环内逐条查 + 改 + retargetThumb，无事务包裹；失败返回 `{error, moved}` 但已移动的部分不回滚。
- **影响**：批移动是用户高频操作，中途失败（如单个文件被占用）后 UI 与磁盘状态分裂；且 N+1 在大选择集下明显慢。
- **修复方向**：`better-sqlite3` 事务包裹全部行更新（磁盘 move 保持逐个 + 失败清单）；循环内查询提到循环外。

### S1-6 【实现】enrichMissingMeta 无并发上限：大库启动时 Promise.all 打满 ffmpeg
- **位置**：`src/main/ipc.ts:278-293`
- **问题**：所有缺 codec 的视频行 `Promise.all` 全部并发 `probeVideo`。
- **影响**：大库启动瞬间 spawn 数百个 ffmpeg 进程，机器卡死；也拖慢启动本身。
- **修复方向**：并发池（p-limit 或信号量，4–8），与 scan.ts 的并发 8 策略对齐。

### S1-7 【设计】全量同步架构：任何变更 → 全量 reload → 全量过滤重渲染
- **位置**：`src/main/ipc.ts:80-88`（assets:changed 无 delta）→ `src/renderer/src/App.tsx:26-79`（订阅即全量 reload）→ `src/renderer/src/store/ui.ts:448-479`（`data.assets` 数组全量替换）→ `src/renderer/src/data/query.ts:168-213`（queryAssets 无 memo、sidebarCounts 全量重算）
- **问题**：watcher 单文件事件也触发整库重拉（IPC 传全量 AssetRow 数组）、内存全量重过滤、React 全量重渲染。
- **影响**：万级素材库中 watcher 高频事件（复制一批文件）会让三进程全链路 O(N) 放大，UI 掉帧甚至无响应；openspec 进行中的 fix-renderer-stability change 自承此域存在已知问题。
- **修复方向**：`assets:changed` 携带 delta（新增/变更/missing 的 id 列表）；渲染层按 id 合并进 store（Map 存储）；queryAssets 按 filter 键 memo（zustand selector 或 useMemo）。

### S1-8 【设计】缩略图懒生成挂起协议请求：首刷网格全部 pending
- **位置**：`src/main/media.ts:65-88`（thumb=1 分支在协议 handler 内同步 await ensureThumb 串行队列）
- **问题**：首次浏览大库时每个缩略图请求都挂在串行队列上，HTTP 语义上表现为海量 pending 连接。
- **影响**：首刷体验差（长时间空白）；且把「生成」这种慢操作耦合进「读取」协议路径，超时/重试行为不可控。
- **修复方向**：① 队列改并发（CPU 密集，sharp 可 2–4 并发）；② 协议请求 miss 时立即返回占位图 + `thumbs:progress` 事件通知渲染层重取；③ 渲染层已有预热机制，可前移预热时机。

### S1-9 【实现】app_state 任意 key 读写：无命名空间的公共垃圾桶
- **位置**：`src/main/ipc.ts:753-757`；`src/preload/index.ts:71-74`；`src/main/services/store.ts:300-307`
- **问题**：`state:get/set` 接受任意 key/value 字符串，渲染层可写任意键（含主进程自用的键）。
- **影响**：键冲突风险（渲染层与主进程谁覆盖谁不可知）；持久化数据无 schema、无校验，违反 AGENTS.md「读取时逐字段校验」在 store 层的对应约束。
- **修复方向**：按命名空间收口（`uiPrefs.*` / `preferences.*` / `window.*`），或预注册键 + 值校验器；渲染层只经 `uiPrefs`/`preferences` 专用 handler。

### S1-10 【实现】library:purgeLegacy 无二次确认直接清空三张表
- **位置**：`src/main/ipc.ts:643-652`
- **问题**：DELETE `asset_tags`/`tags`/`assets` 全部行，无确认参数、无备份、无 dry-run。
- **影响**：渲染层一个误调用即抹掉整库资产记录（文件仍在，但标签/评分/组织结构全丢）。
- **修复方向**：要求显式 `confirm: true` 参数 + 主进程校验；删除前把资产行 dump 到 `.mediahub/backup-<ts>.json`。

### S1-11 【设计】IPC handler 与协议层零测试
- **位置**：`tests/`（24 个测试文件全部落在纯函数与服务层；ipc.ts 763 行、media.ts 124 行无任何直接测试）
- **问题**：handler 与注册/副作用耦合（S1-1 的直接后果），无法单测；media:// 协议 handler 同样不可测。
- **影响**：作用域解析、patch 白名单、Range 解析（media.ts:99-118 手写正则边界）这些高风险纯逻辑都靠手工回归。
- **修复方向**：S1-1 拆分后 handler 变成可注入 db/scope 的函数即可补测；Range 解析、mimeForExtension 等先抽纯函数。

## S2 — 中（错误处理 / 数据层 / 状态管理 / 安全加固）

### S2-1 【设计】错误处理无协议：四种风格并存
- **位置**：`src/main/ipc.ts`（handler 返回 `{error}`）与 throw 混用；`ipc.ts:129-161` queueThumbWarmup catch 静默吞错；`scan.ts` 错误逐文件静默；`src/renderer/src/store/ui.ts` catch 后 `alert()`（L325-331 等 10 处）
- **影响**：无统一错误通道意味着无法做全局错误上报/UI 提示策略；静默吞错让「缩略图失败」「扫描漏文件」对用户与开发者都不可见。
- **修复方向**：定义 `Result<T, AppError>` 风格返回；主进程加轻量 logger（滚动文件）；渲染层统一 toast 通道（见 S2-2）。

### S2-2 【实现】alert() 阻塞式错误提示与 showToast 两套体系并存
- **位置**：`src/renderer/src/store/ui.ts` L35/347/351/359/371/513/526/562/569/581 + `App.tsx:35`
- **问题**：10+ 处 `alert()`（阻塞主线程、体验差、不可测试），同时已有 `showToast`。
- **修复方向**：全部收敛到 showToast；alert 仅保留 window.confirm 类确认（cssDirty 已用 confirm，风格一致）。

### S2-3 【实现】listAssets N+1 标签查询
- **位置**：`src/main/services/store.ts:60-71`
- **问题**：每条资产一次 `tagStmt.all`。
- **影响**：万级库全量列表 = 万次查询；叠加 S1-7 全量 reload，三进程链路最慢点。
- **修复方向**：LEFT JOIN + `GROUP_CONCAT` 一次取回，或按 assetId IN 批量两段查询。

### S2-4 【实现】upsertScanned 对 unchanged 条目也全量 UPDATE
- **位置**：`src/main/services/store.ts:250-254`
- **问题**：判断出 unchanged 后仍调 `writeScanned` 走完整 UPDATE。
- **影响**：启动对账全库 upsert 时写入放大；UPDATE 会改 updated_at，下游「按时间排序/最近导入」语义被污染。
- **修复方向**：unchanged 直接 continue。

### S2-5 【实现】createLibrary 查重两层逻辑不一致
- **位置**：`src/main/services/store.ts:44-49`（path 精确匹配）vs `src/main/ipc.ts:321`（toLowerCase 大小写不敏感）
- **影响**：Windows 大小写不敏感文件系统上，ipc 层拦住了，但任何其它调用点走 store 层即可创建出等价路径的第二个库。
- **修复方向**：查重收敛进 store.createLibrary（大小写不敏感），ipc 层只做 UI 提示。

### S2-6 【实现】分钟精度时间戳
- **位置**：`src/main/services/store.ts:223`（`toISOString().slice(0, 16)`）
- **影响**：同分钟内多次变更无法区分，「最近导入」排序不稳定；与文件 mtime（毫秒）比较时精度错位。
- **修复方向**：保留完整 ISO 毫秒，展示层截断。

### S2-7 【实现】reconcileLibrary 空 entries 不落库：库清空后资产不标 missing
- **位置**：`src/main/ipc.ts:251-275`
- **问题**：`entries.length > 0` 才 upsert。
- **影响**：用户清空/移动整个库目录后，库内资产永远显示为「存在」，ghost 数据。
- **修复方向**：对账语义以「库内扫描结果全集」为准，空结果也应执行 missing 标记；补库清空场景测试。

### S2-8 【实现】WAL checkpoint 时机不足：close→hide 不 checkpoint
- **位置**：`src/main/index.ts:249-255`（仅 window-all-closed）
- **问题**：关闭窗口到托盘（close 拦截 hide）不触发 checkpoint，只有真正 quit 才做。
- **影响**：长期挂后台时 WAL 持续增长；异常断电后恢复慢、丢最近写入的可见性延迟。
- **修复方向**：hide 时也 checkpoint；或库句柄空闲时定期 `wal_checkpoint(PASSIVE)`。

### S2-9 【实现】Ctrl+滚轮列宽每次 tick 落库
- **位置**：`src/renderer/src/App.tsx:158-169`
- **影响**：高频写 app_state（每格一次 IPC + SQLite 写）。
- **修复方向**：滚轮停止后 300ms 防抖 persistUiPrefs（与主窗口 resize 防抖 400ms 的既有策略对齐）。

### S2-10 【设计】shared/types.ts 是 117B 空壳：跨进程类型实际散落两侧
- **位置**：`src/shared/types.ts` vs `src/main/services/store.ts`（AssetRow）vs `src/renderer/src/data/types.ts`（AssetType/AssetFormat）
- **问题**：AGENTS.md 约定「跨进程共享纯类型放 shared」，但该文件近乎空；AssetRow 与渲染层 Asset 靠 `r as unknown` 强转对齐（ui.ts:448-479）。
- **影响**：主/渲染两侧 schema 漂移无编译期防护；preload 的 `assets.list` 返回 `Promise<unknown>`（preload/index.ts:43）使断链更彻底。
- **修复方向**：AssetRow/事件 payload 类型上移 shared；preload 出入参显式类型化，删掉 unknown 强转。

### S2-11 【实现】media:// 错误细节泄漏给渲染层
- **位置**：`src/main/media.ts:120-121`（`500 'error: ' + String(e)`）
- **影响**：内部路径、库结构信息随错误体暴露。
- **修复方向**：500 只回固定文案，细节进主进程日志。

### S2-12 【实现】setWindowOpenHandler 不校验 URL 协议
- **位置**：`src/main/index.ts:163-166`
- **问题**：任何 `window.open` 目标一律 `shell.openExternal`，`file://`、自定义协议也会交给系统。
- **修复方向**：仅放行 `https:`，其余 deny 并记录。

### S2-13 【实现】sandbox:false 无必要
- **位置**：`src/main/index.ts:116-121`
- **问题**：preload 实际只用 `ipcRenderer`/`contextBridge`（94 行全文核实），sandbox:true 可行。
- **修复方向**：开启 `sandbox:true` 并回归验证（AGENTS.md 已要求改 preload 后完整重启验证）。

### S2-14 【实现】dev 调试桥 = 本地任意 JS 执行面
- **位置**：`src/main/index.ts:220-239`（GET /<expr> → executeJavaScript，127.0.0.1:9223）
- **问题**：dev-only，但同机任意进程（浏览器里任何页面对 127.0.0.1:9223 的 GET 也算）可驱动渲染层执行任意 JS——进而经 windowApi 读全库。
- **修复方向**：启动时生成随机 token，路径前缀必须带 token；或仅响应 `Origin` 为 dev server 的请求。
